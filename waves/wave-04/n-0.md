# n-0: critic's report on h-3 (56 operations at 16 points, and the 5/6 rate)

> Editor's note (11 October 2026): this report was written before the paper of Coppersmith, Feig and Linzer (1994) had been read. The 4-point circuit in 7 operations and the rate 7/8 are due to that paper, not to the patent filed in 2002 or to Alman and Rao (2023). See [Earlier papers](../README.md#earlier-papers). What this report says about published work is as its author marked it: read through a tool that summarises, from an abstract, second hand, or from memory. One guess of this report has a printed basis: that the Fourier count of Alman and Rao "should fall too" follows the shape of their Lemma 1.1, which turns a Walsh-Hadamard count c N log N + O(N) into a Fourier count (2c/3 + 28/9) N log N + O(N). Nobody has put a new count into that lemma and checked the result.

**Verdict in five lines.**
1. **The arithmetic holds.** I replayed h-3's files with a checker of my own and rebuilt the whole family with a builder of my own: 56 operations for H x / 2 at 16 points, 4,352 for H x itself at 512 points, and one size further, 45,056 against the textbook's 49,152 at 4,096 points, proved on all unit vectors.
2. **The cost reading holds.** In OpenAI's files a multiplication by any constant, 1/2 included, is one gate, exactly like an addition. Alman and Rao count the same way. So 5/6 against 23/24 is a fair comparison of leading constants.
3. **It is new as far as I can find, but only in one small place:** an 8-point kernel with 19 additions and one halving, where Alman and Rao's published kernel has 22 additions and one halving. Everything else is their published recursion with that kernel put in.
4. **It does nothing for the order, and I can say why it never will.** The growth law is (5/6) N log2 N + (1 + (k mod 3)/6) N, the saving exponent is 0, and a determinant argument (section 6) shows that any program with this family's scale pattern needs at least (1/6) N log2 N additions.
5. **One sentence of the claim must be reworded:** "56 where the list had 60" compares two different outputs. The 60 computes H x / 4, the transform that preserves lengths; the 56 computes H x / 2. For H x / 4 the list's 60 still stands (the best I can make from the 56 is 64), and for H x itself at 16 points the textbook's 64 still stands.

Counts. **(G)**: a gate is any a*u + b*v, scalings free. **(O)**: OpenAI's count, every addition, every subtraction and every multiplication by a constant costs one. This report is about (O) unless it says otherwise.
Words. N = 2^k points. H is the N by N matrix of signs (-1)^(number of common 1-bits of the row number and the column number). "H x exactly" means with no factor in front. The *textbook* program does one layer of N additions and subtractions per address bit: N log2 N operations. A *kernel* is a small circuit for the 8-point transform; applying it along three address bits at a time, block by block, gives the transform at every size (the matrix H at N points is the 8-point one repeated as a tensor product). A *halving* is a multiplication by 1/2.

## 1. The claim, stated exactly

- (a) There is a program of 56 operations (O) at 16 points whose 16 outputs are the rows of H applied to x, each divided by 2. File `h-3-orecord/o_16.txt`.
- (b) There is a program of 4,352 operations (O) at 512 points whose outputs are exactly H x, final multiplications included. The textbook needs 4,608. File `h-3-orecord/ox_512.txt`.
- (c) For N a power of 8 the family costs (5/6) N log2 N + N for H x exactly, and 5/6 is below the leading constant 23/24 of Alman and Rao (2022), the best published.
- (d) The whole thing is g-1's 8-point circuit (19 additions, one halving, output H x / 2) used as a kernel, and the reading that a halving costs one unit in OpenAI's model.

## 2. My own replay  [ran]

Checker `n-0/check.py`, written from nothing, sharing no code with h-3's `orec.py` or e2-0's `ocheck.py`. It reads a program file, refuses a line that is not one operation or that uses a wire before it exists, and then checks twice:
- **A, a proof of the matrix:** it runs the program on all N unit vectors at once in exact integers (inputs scaled by 2^24 so that every halving must divide exactly, or the file is rejected) and compares output j with one common factor times row j of H.
- **B, a second route:** three random integer vectors in exact fractions against the defining sum, with no fast transform anywhere.

## 3. The cost reading, attacked

**What I read in OpenAI's files** (`R/OAI/`, R = the release tree named in the brief). [read]
- `Computability/FourierCircuit/Core.lean`, lines 9 to 12: a gate is `add i j`, `sub i j` or `scale c i` for any complex number c. The size of a circuit is its number of gates. Outputs "name available values, so permutations and arbitrary fanout are uncharged" (line 31). So a halving is one gate, a multiplication by 8 is one gate, and the order of the outputs is free. This is count (O) exactly.
- `Computability/FourierTransform/RAM.lean`, lines 186 to 188: on the machine `add`, `sub` and `scale` are each billed one unit; line 28: "There is no instruction for an arbitrary complex constant", so the scalar 1/2 has to be made once (the number 1, then 1 + 1, then its inverse: three units for the whole program) and 2^m by m more additions. A handful of units, once.
- The reading of a halving as one unit is therefore right, in both of OpenAI's models. **This attack fails.**

**Where the reading needs care.** [read + derived]
- **OpenAI's statements want the matrix exactly.** `Core.lean` line 45: `C.eval x = A.mulVec x`. `Goal.lean` line 58: the result must equal `dft n x`. A program for H x / 2 does not meet a statement of that kind. So the number that counts for an exact statement at 16 points is still the textbook's 64 (the family gives 72 there), and the first size where H x itself is below the textbook is 512. h-3 says this; the brief's one-line summary does not.
- **"56 where the list had 60" compares two different outputs.** e2-0's 60 computes H x / 4, which at 16 points is the transform that preserves lengths (H divided by the square root of N). The 56 computes H x / 2. Turning the 56 into H x / 4 by halving every output costs 72. I found a cheaper way [ran, `n-0/quarter16.py`, `quarter16.txt`, replayed by `check.py`]: replace the last layer's pair (a + b, a - b) by s = a + b, p = s/2, q = p - b, three operations instead of four for the two halved outputs; that gives **64**, still above 60. The honest statement has three columns, as in h-3's own table: any one common factor, 56; H x / sqrt N, 60; H x exactly, 64.
- **Neither of OpenAI's statements is about this matrix or can see a constant.** `Core.lean` lines 47 to 50 ask for the Fourier matrix (not H) in fewer than c n log2 n gates for every c > 0. `Goal.lean` lines 75 to 77 ask for a time that is o(n log n). `RAM.lean` lines 15 to 16 say constant rescalings of the charge "are immaterial". A leading constant of 5/6, or of 1/100, satisfies neither.
- **Alman and Rao's count is the same count.** Their paper counts "field additions and field scalar multiplications" and lets multiplication by 1, -1 and 0 go free [read, through a summarising tool, twice]. OpenAI would charge a bare change of sign and they would not; the files contain none, so the two counts give the same number on these programs.

## 4. Is it known?  [read; searches of 2026-10-11, about 01:08 to 01:12 EDT]

- **The scheme is known and published.** J. Alman and K. Rao, "Faster Walsh-Hadamard and Discrete Fourier Transforms From Matrix Non-Rigidity", arXiv:2211.06459 (v1 11 November 2022, v2 14 June 2023; STOC 2023). Theorem 1.1: H x in at most (23/24) N log N + (13/12) N field operations. Theorem 6.2 gives the split: (22/24) N log N + (N/24)(log N mod 3) additions, (1/24) N log N halvings, N - 1 multiplications by a power of two. Their kernel is 8 points, 22 additions and one halving, returns the transform up to a power of two, and the N - 1 final multiplications repair it. That is, word for word, the structure of `ox_512.txt`.
- **What is not in the paper:** a kernel of 19 additions and one halving. With it their own recursion gives (20/24) = 5/6 where they have 23/24, and (19/24) additions where they have 22/24. They write that "despite some effort" they could not improve further with a 16-point decomposition, and they claim no optimality.
- **Later work: none found.** Five web searches (2024 to 2026, for a better constant, for "19 additions", "20 operations", "5/6 N log N", for small exact circuits), one arXiv query sorted by date and one citing list (`n-0/lit.out`): seven papers cite Alman and Rao in that list, none on this constant; the newest relevant arXiv entries are still the two papers of November 2022. A seminar announcement of November 2024 still gives 23/24. The note `lit-constants.md` (another agent, an hour earlier, a wider search: 14 arXiv queries, two citation indexes, one patent family) reached the same answer; I did not repeat its patent reading.
- **So: new as far as I can find, and the new thing is twenty lines.** Not found is not the same as does not exist. Unsearched: Google Scholar's citing list, paywalled signal-processing journals, the repositories that grew around OpenAI's release.
- **Two cautions about the words "best published constant".**
  - In the limit the best published constant is zero, and it is this project's own: a program in O(n (log n)^(1 - 8.7625e-4)) is below c n log n for every c. So 5/6 against 23/24 is a comparison between explicit programs at sizes one can write down, nothing more.
  - With scalings free, the published number is 7/8 (Alman and Rao's Theorem 6.1; a 2002 patent has the same 4-point trick, by `lit-constants.md`). Name the count every time.

- **Growth law, every power of two:** operations = N (2.5 floor(k/3) + (k mod 3)) + N = (5/6) N log2 N + (1 + (k mod 3)/6) N, at most (5/6) N log2 N + (4/3) N. All eleven sizes I built match it to the unit.
- **The ratio to the textbook is 5/6 + 1/k** for k a multiple of 3. It reaches 5/6 slowly: 0.944 at 512 points, 0.917 at 4,096, 0.900 at 32,768. The "+ N" is the price of giving the factor back.
- **It does not improve with the size of the kernel.** Best known rate (operations per point per address bit, any one common factor): 1 at 2 points, 1 at 4, 5/6 at 8, 7/8 at 16 (this is the 56: one kernel layer and one textbook layer, worse than 5/6), 5/6 at 64 and 512. A 16-point kernel would need 53 operations or fewer to beat 5/6; nobody has one. Linear size would need this rate to fall like a constant over log2 of the kernel size. What is observed is flat.

## 6. What known theory says about "linear or not"  [derived, from Morgenstern's 1973 argument]

Two facts, the second one sharper than what h-3 wrote.

- **A fixed kernel can never change the order.** A kernel of s operations on q points gives exactly (s / (q log2 q)) N log2 N. Below N log N in order needs a family of kernels whose rate tends to zero, which is the original problem again.
- **This family is on the wrong side of the determinant.** Take any program made of additions, subtractions and multiplications by constants. Look at the largest determinant of any square block of the table of all its wires. An addition at most doubles it; a multiplication by c multiplies it by at most max(1, |c|). The outputs c H have determinant |c|^N N^(N/2). Hence
  (number of additions and subtractions) + (sum of log2 max(1, |c_i|) over the multiplications) >= (N/2) log2 N + N log2 |c|.
  - The kernel layers produce H x / 2^(k/3) using halvings only (which add nothing to the left side). So **any** program with that output and such constants has at least (N/2) log2 N - N k/3 = **(1/6) N log2 N additions**. The family has (19/24) N log2 N. It lives between 1/6 and 19/24 and cannot leave N log N, whatever is done inside.
  - The bound vanishes only when the inner program produces H x divided by about the square root of N, the length-preserving transform. The 8-point kernel divides by 2 per three address bits; the determinant asks for the square root of 8, about 2.83. e2-0's family (rate 7/8) does divide by the square root of N, so it sits where the determinant says nothing. **The count-(O) record and the only place where a linear program could live are two different places.**
  - For that place the published barriers are the ones in the floor note: programs whose intermediate tables stay well conditioned need order N log N (Ailon, 2013 to 2016, as read by the earlier readers; I did not reread them). A linear program must compute the length-preserving transform through badly conditioned intermediate states, or use constants that carry about (N/2) log2 N bits between them. Nothing in h-3 does either.

## 7. In the user's terms

- **Circuit size for n = 2^k points, count (O), H x exactly:** n (2.5 floor(k/3) + (k mod 3)) + n, at most (5/6) n log2 n + (4/3) n. Below the textbook from 512 points on.
- **Saving exponent: 0.** The order is n log n. Not linear, and by section 6 not on a road to linear.
- **Against the published 8.7625e-4:** no effect on the exponent [h-3's reading of the engine, not checked by me]. For scale only: the published saving factor (log n)^(8.7625e-4) reaches 6/5 when log n is about e^208, roughly 10^90 [derived, constants ignored]. Below that size a constant 5/6 is the larger gain against the textbook; it is still only a constant, and a statement that asks for o(n log n) does not see it.
- **What it is worth:** a small, exact, checkable improvement of a constant in a 2022 STOC paper: 20/24 for 23/24 in all operations, 19/24 for 22/24 in additions, crossover at 512 points where theirs is near 2^24 [the last figure from `lit-constants.md`]. Their Fourier-transform constant 15/4 is obtained by calling their Walsh-Hadamard algorithm, so it should fall too [guess, not computed].

## 8. What fails, and the nearest true statements

- **Fails as worded:** "56 at 16 points, where the list had 60". Smallest case: 16 points itself. Nearest true statements: (i) among programs whose outputs are one common multiple of H x, 56 at 16 points (factor 1/2); (ii) for H x / 4 the best on file is still 60 (64 from this family); (iii) for H x exactly the best on file is still the textbook's 64, and the family first wins at 512 points.
- **True but easy to overread:** "the 5/6 rate". At 512 points the ratio to the textbook is 0.944, not 0.833; the rate is a limit, with ratio 5/6 + 1/k.
- **True only with its qualifier:** "below the published 23/24". Add: for explicit programs at ordinary sizes, all operations charged; in the limit the published constant is already zero.
- **Does not fail:** the two files, the cost of a halving, the equality of Alman and Rao's count with OpenAI's on these programs, the growth law.
